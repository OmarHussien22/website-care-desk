# Coursaty mobile_base Constitution

## Core Principles

### I. State & Navigation (GetX-only)

GetX is the SOLE state management framework. Riverpod, Bloc, Provider, and `ChangeNotifier`
MUST NOT be introduced. All navigation MUST go through GetX named routes declared in
`AppRoutes` and registered in `AppRouter.pages`. `go_router` and direct `Navigator.push` /
`Navigator.pop` calls are PROHIBITED in feature code.

**Rationale**: A single navigation and state model keeps controllers, bindings, and
route arguments uniform across features, and avoids the lifecycle and dependency-injection
divergence that mixed solutions create.

### II. Feature-First Clean Architecture

Every feature MUST follow the pipeline:

> `Controller → UseCase → Repository → ApiService → ServicesInterface → Dio`

The Repository MUST return `DataState<T>` (`DataSuccess` or `DataFailed`). Callers MUST
NOT wrap `useCase()` invocations in `try`/`catch` — error propagation is the pipeline's
responsibility. The `auth` feature is the canonical reference; new features MUST
replicate its layering, file structure, and binding pattern.

**Rationale**: A uniform pipeline makes features substitutable, testable, and reviewable
without per-feature reasoning about error handling or layer ownership.

### III. Type & Null Safety

The `!` (bang) operator MUST NOT be applied to untrusted nullables (API responses,
controller state, user input). Use `?.`, `?? fallback`, or explicit `if (x == null)`
checks instead. Every `TextEditingController` (and any other disposable controller)
MUST be disposed in the owning GetX controller's `onClose()`.

**Rationale**: Bangs hide runtime crashes that survive `flutter analyze`; undisposed
controllers leak memory and break hot-reload state in long-running sessions.

### IV. UI & Styling Discipline

- Raw pixel literals are PROHIBITED in widget code. Use the screenutil helpers:
  `.toW`, `.toH`, `.toFS`, `.ESH`, `.ESW`, `.toRad`.
- Hardcoded `Color(...)` / `Colors.*` values are PROHIBITED. Use `AppColors.get.*`.
- Raw `Text(...)` widgets are PROHIBITED in pages and reusable widgets. Use
  `CustomText`.
- The `google_fonts` package MUST NOT be added. Only the bundled URW / Montserrat
  font assets are permitted.

**Rationale**: Consistent scaling, theming, and typography are required across screen
sizes and dark/light themes; per-widget overrides defeat the design system.

### V. Observability

`print()` MUST NOT appear in committed code. Use `log('msg', name: 'ClassName')` from
`dart:developer`, or `printDM()`. Sentry is the production error monitoring channel
and MUST remain wired in `main.dart`'s zone/error handlers.

**Rationale**: Structured, named logs are filterable in DevTools and shippable to
Sentry; bare `print` calls pollute release builds and are not searchable.

### VI. Testability & App Modes

Every new `Repository` MUST expose a `testData` source. The three app modes
(`prod`, `dev`, `test`) MUST be honored end-to-end:

- `prod` → hits the live network via `Dio`.
- `dev` → returns `devData` and MUST NOT hit the network.
- `test` → returns `testData` and MUST NOT hit the network.

**Rationale**: Deterministic fixtures unblock UI work offline, keep test suites
fast and hermetic, and make demo builds reproducible.

### VII. Quality Gate (Pre-Commit)

The following MUST hold before any commit:

- `flutter analyze .` passes with **zero** errors. Warnings introduced by the
  change SHOULD be resolved or explicitly justified in the PR.
- Every new route is registered in BOTH `AppRoutes` AND `AppRouter.pages`.
- Every new API URL is added to the `ApiNames` mixin.

**Rationale**: Cheap, mechanical checks catch the most common regressions
(missing route bindings, orphaned URL strings, lint drift) before review time.

## Additional Constraints

**Technology stack (authoritative)**:

- Framework: Flutter (Dart, null-safe).
- State management & DI: `get` (GetX) only.
- Networking: `dio` accessed strictly through `ServicesInterface`.
- Sizing: `flutter_screenutil` via the project's extension helpers.
- Logging: `dart:developer` `log()` and `printDM()`. Sentry for production.
- Fonts: bundled URW / Montserrat assets.

**Prohibited dependencies** (do not add without an amendment):
`flutter_riverpod`, `flutter_bloc`, `provider`, `go_router`, `google_fonts`,
`auto_route`, and any alternative HTTP client wrapping replacement for `Dio`.

## Development Workflow

- New feature work MUST follow the auth feature's directory layout
  (`controller/`, `usecase/`, `repository/`, `api_service/`, `model/`, `binding/`,
  `view/`) and naming conventions.
- Repositories MUST return `DataState<T>`; controllers MUST branch on
  `DataSuccess` / `DataFailed`.
- Route changes MUST update `AppRoutes` constants AND `AppRouter.pages`
  in the same commit.
- API endpoint additions MUST land in the `ApiNames` mixin in the same commit
  as the calling `ApiService`.
- `WORKFLOW_RULES.md` is the source of detailed conventions, code templates,
  and utility references. When `WORKFLOW_RULES.md` conflicts with this
  constitution, this constitution wins; `WORKFLOW_RULES.md` MUST then be
  updated to reconcile.

## Governance

This constitution supersedes informal practice and ad-hoc style guides for the
`mobile_base` repository. PRs and reviews MUST verify compliance with
Principles I–VII. Reviewers are expected to block merges that violate a
principle without an accompanying amendment.

**Amendment procedure**:

1. Propose the change in a PR that edits this file and, if affected,
   `WORKFLOW_RULES.md` and the relevant `.specify/templates/*`.
2. Justify the change in the PR description; deviations from a principle
   require an explicit Complexity Tracking entry in the affected plan.
3. Bump `Version` per semantic-versioning rules:
   - MAJOR: removing or redefining a principle in a backward-incompatible way.
   - MINOR: adding a principle or materially expanding guidance.
   - PATCH: clarifications, typo fixes, non-semantic refinements.
4. Update `Last Amended` to the merge date (ISO `YYYY-MM-DD`).

**Compliance review**:

- `flutter analyze .` is the automated gate (Principle VII).
- `/speckit-analyze` SHOULD be run on any feature spec touching navigation,
  networking, or state to confirm alignment with Principles I, II, and VI.
